# 会话记录：自维护无线网络库（802.1X / EAP）+ 软开关看门狗

日期：2026-09-18　仓库：`D:\Files\Develop\Windows\NetworkGuardian`（提交 `a8e6ce0` → `d296834` 及后续文档提交）

需求原文要点：

1. 对 EAP 网络支持自己维护账号密码，建立一个**软件自维护、独立于系统**的无线网络库；
2. 启用无线功能后，保证**所有无线网卡的软开关被打开，间隔 3 秒检查一次并立即打开**；
3. 然后在已保存网络中继续连接处理，遇到 EAP 认证就用自维护库里的信息；失败**重试 5 次**，
   5 次失败后对该网卡**临时放弃**该网络（下次启动依旧继续尝试）。

## 2. 关键决策

| 决策 | 理由 |
| --- | --- |
| 账号密码存**库文件**，不进 `config.json` | 配置是「可分享、可复制」的文本；库文件单独一份、密码以 DPAPI 密文保存，语义清楚 |
| 密码字段 `[JsonIgnore]`，落盘只有 `passwordProtected` | 「明文永不落盘」可以被测试断言（`WifiNetworkVaultTests`） |
| 凭据走 `WlanSetProfileEapXmlUserData`，配置 XML 里不放账号 | 真机实测：放进去会被 `WlanSetProfile` 以原因码 524289 拒绝 |
| 配置按「指纹 + 应用时间」判断是否重写 | 既能在库改动后重写，也不会每轮重复写系统配置 |
| 失败计数只放内存 | 需求明确「下次启动依旧继续尝试」，持久化黑名单会违背它；短期频繁失败另由既有 `ConnectFailureBlacklist` 处理 |
| 看门狗是独立循环而非复用监测循环 | 监测循环的心跳是低频巡检，且引擎的无线电动作有限流（12 次/小时、最小间隔 30 秒），都不适合「3 秒内必须打开」 |
| WPA3-Enterprise 拒绝生成 | 三种取值 × 三块网卡全部被 WLAN 服务以 1206 拒绝；宁可明确要求自定义 XML，也不产出无效配置 |
| 指纹用自写 FNV-1a 而非 SHA256 | 只用于「是不是同一份文档」，不需要密码学强度（实测换过来体积无变化，8.24 MB 前后一致，理由是不引入密码学依赖） |

## 3. 真机验证（证据摘要）

| 项目 | 结果 |
| --- | --- |
| 企业级配置写入/读取/删除 | 5 种形态（PEAP/MSCHAPv2、WPA-TKIP、隐藏网络手动、EAP-TLS、EAP-TLS 固定证书）：`apply success=True`，二次 apply 判定「无需更新」，改条目后 `LibraryChanged`，测试配置全部删除 |
| 真实 802.1X 失败计数 | 用假身份连真实 AP：5 次失败（每次 18 s 超时）→ `Failures=5`、`abandoned=True`；`ClearEapRetries` 后立即可再试 |
| 密码保护 | 库文件里 grep 不到明文；重新加载能解出密码；DPAPI 密文换密钥后解不出并给出提示 |
| 软开关看门狗 | 程序运行中关掉一块网卡软开关：第 1 轮 0.26 s（通知路径）、第 2 轮 2.29 s、第 3 轮 2.30 s（看门狗行），全部恢复为 `Software On` |
| 发布包 | 8.24 MB 单文件；`tools/verify-portable.ps1` 33 项全通过（含干净环境启动、助手真实执行、关闭链路、无残留） |
| 凭据库页面交互 | `tools/qa-ui-click.ps1 -Page credentials`：命中区域与绘制位置一致——`y=240` 一行上 x=280/340 命中 8（保存并应用）、400/460 命中 9（新增网络）、520/580 命中 10（重新加载）；点「新增网络」后命中目标数 **11 → 32 → 53**（每张完整条目卡片新增 21 个命中区域），点「重新加载」回到 11，说明自绘控件的命中链（按下/抬起 + 命中索引 + 回调）在新页面上成立 |
| 配置的可见范围 | `WifiProfileVisibilityExploration`：刚写到 A 卡时只有 A 卡能看到；数秒后 B/C 卡也会看到（用户配置存储是机器级、各接口视图异步跟进）；`RemoveEverywhere` 后三张卡都为 0。附带结论：不带 `interface=` 的 `netsh wlan show profiles` 会按网卡重复打印同一份用户配置列表 |

防御性设计（避免验证过程误伤用户环境）：真机用例使用独立配置名 `NG-SELFTEST-HXXY`、假身份
`selftest@example.invalid`、`connectAutomatically=false`，并在 `finally` 中删除配置且断言用户自己的同名配置仍存在；
看门狗验证脚本使用临时配置根并把掉线宽限调到 900 秒，保证验证期间不会触发连接动作。

## 6. 过程中的缺陷 / 根因

见 `docs/eap-credential-library.md` 第 9 节（凭据不能进配置 XML、EAP 用户数据 XML 命名空间与顺序、
EAP-TLS 元素顺序、WPA3 不可用、`radio_state` 写不了、库返回活对象、引擎限流、`WLAN_PROFILE_USER` 假设错误、
用户配置异步扩散导致单卡删除留残留）。

另外修掉一个**验证工具自身**的问题：`tools/qa-ui-click.ps1` 靠「先点 (4,4) 量一次坐标缩放」来补偿 DPI，
而实测同一台机器上这个系数会在 1.25 与 1.5 之间变化（取决于启动该脚本的进程的 DPI 感知上下文），
导致同一组坐标两次运行点到不同位置。现在脚本先调用
`SetThreadDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)`，系数稳定为 1.0，
坐标即为真实客户区坐标（校准仍保留，作为「系数是否为 1」的断言）。

## 7. 验证基础设施缺陷

1. **硬件测试并行执行会互相踩**：两个硬件测试类同时跑时，`WlanSetProfile(overwrite: true)` 返回
   `ERROR_183`（文件已存在）——不是「硬件不稳定」，而是真的撞车。三个真机测试类现在共享
   `[Collection("wifi-hardware")]`（`DisableParallelization = true`），单元测试仍并行。
2. **单卡删除会留下真实残留**：用户配置会异步扩散到全部网卡，只删写入时那张卡会让另外两张留着同名配置
   （检查机器时发现的 `NG-SELFTEST-HXXY` 就是这么来的）。清理改为逐网卡删除 + 读回校验，测试在 `finally`
   断言三张卡都无残留；机器上遗留的测试配置已用手工 `netsh wlan delete profile` 清理，用户自己的
   `HXXY-WiFi` 未受影响。
3. **`WlanSetProfile(overwrite: true)` 对「正在被使用的同名配置」返回 `ERROR_183`**：上一轮遗留的测试配置
   让下一次写入直接失败。`WifiProfileApplier` 现在遇到 183/80 会先删除再写入，日志留一行 warning；
   修好后同一份带残留的机器上硬件用例可重复通过。
